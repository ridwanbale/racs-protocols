# RACS Engineering Instructions

## Project purpose

RACS is a risk-aware coordination layer for heterogeneous autonomous systems.

The current development objective is a technically credible and reproducible
V1 warehouse simulation experiment demonstrating that early risk detection
plus coordinated intervention can reduce the system-level impact of a
localized degradation.

## V1 hypothesis

The V1 experiment should test:

A localized operational degradation can be detected before it cascades,
and RACS intervention reduces downstream system degradation relative to
an otherwise equivalent baseline without RACS.

## Architectural principles

1. Keep RACS separate from the underlying robot or warehouse implementation.
2. Robot/platform-specific functionality belongs behind adapters.
3. Keep risk detection separate from coordination policy.
4. Keep coordination policy separate from simulation mechanics.
5. Safety constraints override optimization objectives.
6. Prefer explicit typed interfaces and configuration over hidden coupling.
7. Do not introduce production infrastructure unless required by the experiment.
8. Kafka and ROS 2 are out of scope for V1 unless explicitly requested.
9. Do not hard-code experimental results.
10. Experimental outputs must be generated by executable code.
11. Experiments must be deterministic when given the same seed and configuration.
12. Preserve existing public APIs unless a change is explicitly justified.

## V1 scope

Prioritize:

- deterministic simulated time
- parameterized scenarios
- progressive localized degradation
- risk detection
- coordination intervention
- meaningful command semantics
- baseline versus RACS comparison
- multi-seed experiments
- structured experiment outputs
- reproducibility
- tests

Do not expand V1 into:

- production Kafka
- production ROS 2
- Kubernetes
- cloud deployment
- physical robots
- distributed production infrastructure
- generalized multi-industry simulation

unless explicitly requested.

## Experiment integrity

Never manufacture, hard-code, or manually adjust benchmark results.

Every reported experimental metric must be traceable to simulation output.

Record enough configuration to reproduce an experiment, including:

- random seed
- scenario
- simulation parameters
- risk thresholds
- intervention policy
- relevant software/config version

Baseline and RACS conditions must differ only in the intervention being tested
unless the experiment explicitly documents another difference.

## Development workflow

Before substantial implementation:

1. Inspect relevant existing code.
2. Explain the proposed change.
3. Identify files/components affected.
4. Implement the smallest coherent change.
5. Add or update tests.
6. Run relevant tests.
7. Run the full test suite when appropriate.
8. Report failures rather than hiding or bypassing them.
9. Show the resulting git diff.

Do not refactor unrelated code while implementing a scoped task.

## Testing

Use the repository virtual environment:

```powershell
.\.venv\Scripts\python.exe
```

The current pre-V1 baseline is:

```text
49 tests passing.
```

On this Windows Codex environment, pytest cache creation may emit an
Access Denied warning. If necessary for verification, run pytest with:

```powershell
.\.venv\Scripts\python.exe -m pytest tests/ -q -p no:cacheprovider
```

Do not treat cache-provider failure itself as an application test failure.

## Git

Do not commit unless explicitly instructed.
Do not push unless explicitly instructed.
Do not rewrite Git history.
Do not delete source files unless the requested change requires it.
Do not mix unrelated cleanup with functional changes.
